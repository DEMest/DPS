# Task J2: синхронизированный доступ к списку

Программа хранит список строк. Ты вводишь строки, и они попадают в начало списка. В это же
время несколько нитей бесконечно сортируют список пузырьком, причём медленно, с задержками.
Поэтому пустой строкой в любой момент можно посмотреть, как идёт сортировка.

Есть две версии списка:

* `linked` — свой связный список, у каждой записи своя блокировка (основная часть задания);
* `sync` — `ArrayList` в обёртке `Collections.synchronizedList()` (вторая часть задания).

## Запуск

Нужен JDK 21 или новее. **Все команды выполняются из папки `J2`:**

```
cd DPS/J2
./gradlew jar                      # собрать build/libs/J2.jar (в Windows: gradlew.bat jar)
java -jar build/libs/J2.jar        # запустить
```

| Опция | Что делает |
|---|---|
| `--list linked` | свой связный список (по умолчанию) |
| `--list sync` | `ArrayList` + `synchronizedList` |
| `--threads <n>` | сколько нитей сортируют, по умолчанию 2 |
| `--inner-delay <мс>` | задержка внутри шага, по умолчанию 1000 |
| `--delay <мс>` | задержка между шагами, по умолчанию 1000 |

Что вводить:

* **любую строку** — она встаёт в начало списка; строка длиннее 80 символов режется на части по 80;
* **пустую строку** (просто Enter) — программа покажет список;
* **Ctrl+D** (в Windows — Ctrl+Z и Enter) — выход.

Пример: ввели четыре строки, через полторы секунды нажали Enter, ещё через восемь — снова
Enter, потом Ctrl+D.

```

Вводите строки. Пустая строка — показать список, Ctrl+D (в Windows Ctrl+Z и Enter) — выход.

delta
```

## Как работает свой список

```
head → a → b → c → null        у каждой записи свой ReentrantLock
```

`head` — пустая запись перед первой. Она нужна, чтобы у первых двух записей тоже была
«предыдущая» и перестановка всегда делалась одинаково.

**Шаг сортировки** — попытка поменять местами две соседние записи:

1. захватить три записи подряд: `prev`, `a`, `b` — всегда по порядку от головы;
2. подождать (задержка внутри шага);
3. если `a > b` — переставить **ссылки** (строки остаются в своих записях):
   ```
   prev → a → b → c     ⇒     prev → b → a → c
   ```
4. отпустить все три записи;
5. подождать (задержка между шагами). В это время нить **ничего не держит**, поэтому список
   можно сразу вывести.

Проход всегда идёт от головы до хвоста, даже если список уже отсортирован. Потом начинается
следующий проход.

**Почему нет взаимной блокировки.** Все нити захватывают записи только по порядку от головы к
хвосту. Нить, которая ждёт запись, держит только записи перед ней. Чтобы нити заблокировали
друг друга, кто-то должен был бы держать дальнюю запись и ждать ближнюю, а так не бывает никогда.

**Вывод** — обычный for-each. Итератор идёт «рука за руку»: держит текущую запись, захватывает
следующую и только потом отпускает текущую. Пока запись захвачена, её нельзя переставить с
соседом, значит, ни одна запись не перепрыгнет через неё. Поэтому каждая строка выводится ровно
один раз: число и содержимое строк всегда правильные, даже если сортировка идёт прямо сейчас.

**Вставка в начало** меняет только `head.next`, поэтому захватывает одну голову.

Весь список целиком не блокируется никогда.

## Как работает версия на `synchronizedList`

`synchronizedList` защищает каждый вызов (`get`, `set`, `add`) по отдельности, а шаг состоит из
нескольких вызовов: прочитать две строки, сравнить, записать обратно. Если между ними
вмешается другая нить или в начало вставят строку (индексы сдвинутся), одна строка задвоится,
а другая пропадёт. Поэтому шаг целиком, вместе с задержкой внутри шага, выполняется в
`synchronized (list)`. Захватить отдельные элементы у `synchronizedList` нельзя — только весь
список.

Обходить `synchronizedList` тоже можно только под `synchronized (list)`. Поэтому итератор под
блокировкой снимает копию списка, и for-each идёт по копии.

## Сколько шагов: теория и замер

Обозначения: `N` — число нитей, `T` — время, `d_вн` — задержка внутри шага, `d_между` —
задержка между шагами.

**Теория.**

* Одна нить делает один шаг за `d_вн + d_между`, за время `T` — `T / (d_вн + d_между)` шагов.
* **Свой список:** нити держат только по три соседние записи и не мешают друг другу, поэтому
  `N` нитей делают в `N` раз больше:
  `S = N · T / (d_вн + d_между)`.
* **`synchronizedList`:** пока одна нить ждёт внутри шага, весь список занят, и шаги идут строго
  по одному. На каждый шаг уходит минимум `d_вн`, поэтому больше `T / d_вн` шагов не сделать,
  сколько бы ни было нитей:
  `S = min(N · T / (d_вн + d_между), T / d_вн)`.

Для задержек по 1 с и `T` = 60 с:

| Нитей | свой список | synchronizedList |
|---|---|---|
| 1 | 30 | 30 |
| 2 | 60 | 60 |
| 4 | 120 | 60 |
| 8 | 240 | 60 |

**Замер** (`Bench.java`): оба списка заполняются одними и теми же 50 строками, нити сортируют
каждый из них заданное время, считаются шаги.

```
java -jar build/libs/J2.jar bench --threads 4 --duration 60 --delay 1000 --inner-delay 1000
```

Без опций (`java -jar build/libs/J2.jar bench`) — 4 нити, задержки по 100 мс, по 10 секунд на
список. Все опции — `bench --help`.

Результаты (macOS, JDK 21), факт / теория:

| Нитей | задержки | свой список | synchronizedList |
|---|---|---|---|
| 1 | 1 с, T = 60 с | 30 / 30 (100 %) | 30 / 30 (100 %) |
| 4 | 1 с, T = 60 с | 102 / 120 (85 %) | 59 / 60 (98 %) |
| 8 | 1 с, T = 60 с | 140 / 240 (58 %) | 59 / 60 (98 %) |
| 4 | 100 мс, T = 60 с | 1142 / 1200 (95 %) | 581 / 600 (97 %) |
| 8 | 100 мс, T = 60 с | 2234 / 2400 (93 %) | 580 / 600 (97 %) |

**Почему так.**

* **`synchronizedList` не растёт с числом нитей.** 4 и 8 нитей делают одни и те же 59 шагов:
  весь список почти всё время занят чьим-то шагом, остальные нити ждут в очереди.
* **Свой список растёт с числом нитей, но вначале отстаёт от теории.** Все нити стартуют с
  головы списка и сначала ждут друг друга, стоя «паровозиком». Каждое ожидание отодвигает нить
  от впереди идущей. Когда между нитями набирается по три записи, они перестают мешать друг
  другу и идут с полной скоростью. За минуту с задержкой 1 с каждая нить успевает сделать всего
  ~30 шагов, поэтому паровозик ещё не разошёлся (58–85 %). С задержкой 100 мс за минуту
  получается ~300 шагов на нить, паровозик успевает разойтись, и результат почти совпадает с
  теорией (93–95 %).
* **Оставшиеся несколько процентов** — накладные расходы: `Thread.sleep` просыпается чуть позже
  заказанного, плюс захват и освобождение блокировок. При задержке 1 с это незаметно, при
  100 мс — 3–7 %.

Итог: свой список с `N` нитями сортирует примерно в `N / 2` раза быстрее, чем
`synchronizedList` (при равных задержках). При 8 нитях и задержке 100 мс — 2234 шага против
580, почти в 4 раза.

## Тесты

```
./gradlew test
```

Около 10 секунд. Проверяется:

* строки встают в начало, длинные режутся по 80 символов в правильном порядке;
* проход сравнивает каждую пару, даже если список уже отсортирован;
* при сортировке переставляются сами записи (те же объекты), а не строки внутри них;
* шаг держит только три соседние записи, остальные свободны;
* 4 нити доводят список до отсортированного (обе версии);
* 8 нитей сортируют без задержек, а тест одновременно добавляет строки и выводит список:
  каждый вывод должен содержать ровно добавленные строки (обе версии; если бы нити
  заблокировали друг друга, тест упал бы по таймауту);
* вывод не ждёт, пока нить спит между шагами (обе версии);
* теоретические числа и короткий замер: свой список делает в разы больше шагов, чем
  `synchronizedList`.

# Task J3: асинхронный обход ресурсов HTTP-сервера

«Паук» обходит HTTP-сервер задачи: запрашивает `/`, затем все пути из поля `successors`
каждого ответа, и так до конца. Результат — все полученные сообщения, отсортированные в
лексикографическом порядке. Каждый URL обрабатывается в своей **виртуальной нити** (Java 21),
поэтому все известные запросы ждут ответа одновременно.

## Задание кратко

Выдан `Task_J3-server.jar` — HTTP-сервер. На `GET` по пути он отвечает `200` и JSON:

```
{"message": "some text", "successors": ["path_1", "path_2", …]}
```

Каждый путь из `successors` — снова URL сервера с ответом того же вида. Ответ может идти
от 0 до 12 секунд. Нужно собрать сообщения со всех URL, начиная с `/`, и вывести их
отсортированными. Предполагается использовать виртуальные нити; сервер устроен так, что
при одновременных запросах всё собирается не дольше чем за 120 секунд.

## Запуск

Нужен **JDK 21 или новее** (`java -version`). **Все команды — из папки `J3`.**

### 1. Сервер

`Task_J3-server.jar` в репозиторий не кладётся (см. `.gitignore`), его нужно положить в папку
`J3` самому. `student_id` — свои имя и фамилия латиницей подряд:

```
java -jar Task_J3-server.jar IvanIvanov
```

Сервер пишет `Running server on port 8080...` и работает, пока его не остановить (Ctrl+C).

> **Порт указывать нельзя.** В задании написано, что можно `java -jar Task_J3-server.jar IvanIvanov 3000`,
> но выданный jar с портом падает: `ClassCastException: class java.lang.String cannot be cast to class java.lang.Number`
> (номер порта передаётся в Jetty строкой). Без порта сервер всегда слушает **8080** — на этот
> порт «паук» и настроен по умолчанию. Если 8080 занят другой программой, её нужно остановить.

### 2. «Паук»

В другом окне терминала:

```
./gradlew jar                                   # собрать build/libs/J3.jar (в Windows: gradlew.bat jar)
java -jar build/libs/J3.jar                     # обойти сервер, вывести сообщения
java -jar build/libs/J3.jar --out messages.txt  # то же, но сообщения — в файл
```

Сообщения печатаются в stdout по одному на строку, ход работы и итог — в stderr, поэтому
`java -jar build/libs/J3.jar > messages.txt` тоже записывает в файл только сообщения.

| Опция | Что делает |
|---|---|
| `--host <адрес>` | адрес сервера, по умолчанию `localhost` |
| `--port <порт>` | порт сервера, по умолчанию `8080` |
| `--url <адрес>` | адрес целиком, например `http://192.168.1.10:8080` (вместо `--host` и `--port`) |
| `--start <путь>` | с какого пути начинать, по умолчанию `/` |
| `--timeout <сек>` | сколько ждать ответа на один запрос, по умолчанию 30 |
| `--retries <n>` | сколько раз повторять неудачный запрос (обрыв, таймаут, 5xx), по умолчанию 2 |
| `--progress <сек>` | как часто печатать ход работы, по умолчанию 5; `0` — не печатать |
| `--out <файл>` | записать сообщения в файл (UTF-8), а не в stdout |
| `--json` | вывести сообщения JSON-массивом, а не по строке |
| `--verbose` | печатать каждый запрос: путь, время ответа, имя виртуальной нити |
| `--help` | справка |

Код завершения: `0` — всё собрано, `1` — какие-то URL получить не удалось (они перечислены в
конце), `2` — ошибка в аргументах.

Пример (`student_id` = `IvanIvanov`):

```
$ java -jar build/libs/J3.jar --out messages.txt

11:58:09.645 [progress]   5 с: найдено URL — 153, получено ответов — 53, ждут ответа — 100, ошибок — 0
11:58:14.647 [progress]  10 с: найдено URL — 227, получено ответов — 127, ждут ответа — 100, ошибок — 0
…
11:59:24.662 [progress]  80 с: найдено URL — 1000, получено ответов — 999, ждут ответа — 1, ошибок — 0
11:59:29.662 [progress]  85 с: найдено URL — 1001, получено ответов — 1000, ждут ответа — 1, ошибок — 0
11:59:34.019 [main] Сообщения записаны в …/J3/messages.txt
11:59:34.019 [main] Готово за 89,3 с: обойдено URL — 1001, сообщений — 1001, ошибок — 0; максимум одновременных запросов — 100
```

С `--verbose` виден каждый запрос и виртуальная нить, которая его выполняла:

```
11:58:05.030 [spider-1] GET / — 200 за 0,38 с, переходов: 100
11:58:05.285 [spider-29] GET /149 — 200 за 0,25 с, переходов: 1
11:58:05.486 [spider-74] GET /412 — 200 за 0,44 с, переходов: 1
```

**Пустые сообщения.** Сервер генерирует сообщения длиной от 0 до 63 символов, поэтому среди них
есть пустые (для `IvanIvanov` — 18 штук). Пустая строка в лексикографическом порядке меньше
любой другой, так что вывод начинается с пустых строк — это не ошибка. С `--json` они видны
явно как `""`.

**Порядок** — `String.compareTo`, то есть по кодам символов: цифры < заглавные латинские <
строчные латинские; если одна строка — начало другой, она идёт раньше. Одинаковые сообщения
с разных URL остаются в выводе все.

## Как это устроено

```
время →     0 с        2 с        4 с        6 с        8 с        10 с       12 с
spider-1    GET / → 100 путей, запущено 100 нитей
spider-2      GET /425 ·························· ответ → новая нить: GET /467 ·········· …
spider-3      GET /225 ··· ответ → новая нить: GET /90 ·················· ответ → …
…
spider-101    GET /638 ················································ ответ → …
                 └── все 100 запросов ждут ответа одновременно, каждая ветка идёт вглубь сама
```

* **Одна виртуальная нить на URL.** Как только в ответе появился новый путь, под него сразу
  запускается своя нить (`Executors.newThreadPerTaskExecutor(Thread.ofVirtual()…)`), запрос
  уходит, не дожидаясь соседей. Обход не идёт «по уровням»: быстрая ветка уходит вглубь, пока
  медленная ещё ждёт ответа. Поэтому общее время равно самой медленной цепочке
  «страница → её successor → …», а не сумме задержек.
* **Почему именно виртуальные нити.** Нить почти всё время просто ждёт ответа сервера (до 12 с).
  Блокирующий `HttpClient.send` в виртуальной нити не держит нить ОС: виртуальная нить
  снимается с нити-носителя, а та выполняет другие. Сотни одновременных ожиданий обслуживает пул
  из нескольких нитей ОС (по числу ядер), а код остаётся простым и последовательным: «запросил —
  разобрал — запустил детей — дождался детей», без колбэков и `CompletableFuture`-цепочек.
  С обычными нитями пришлось бы держать по нити ОС на каждый ожидающий запрос либо
  ограничить пул и тогда ждать дольше.
* **Каждый путь запрашивается ровно один раз.** Перед запуском нити путь добавляется в
  `ConcurrentHashMap.newKeySet()`; `add` атомарен и возвращает `false`, если путь уже есть. Если
  две нити одновременно нашли один путь, запрос отправит только одна. Циклы (ссылка назад на
  `/`) тоже не страшны.
* **Как понять, что обход закончен.** Нить, обработав свой URL, ждёт нити, которые сама
  запустила (`Future.get`; ожидание виртуальной нити тоже почти ничего не стоит). Значит,
  когда завершилась корневая задача, завершились и все остальные — новых путей больше не будет.
* **Ошибки.** Обрыв соединения, таймаут и ответ 5xx повторяются (`--retries`), ответ 4xx —
  сразу ошибка. URL с ошибкой попадает в список ошибок и не прерывает обход остальных.
* **Результат.** Сообщения хранятся в `ConcurrentHashMap<путь, сообщение>`; после обхода
  значения сортируются обычным `Collections.sort`.
* **Пути.** Сервер присылает пути без косой черты (`"425"`), запрашивается `/425`; путь с косой
  чертой берётся как есть.

## Как устроен выданный сервер

Сервер написан на Clojure, исходники лежат прямо внутри jar (`server.clj`, `topology.clj`,
`utils.clj`; посмотреть: `unzip -p Task_J3-server.jar topology.clj`). По ним:

* страниц ровно **1000**, пути `/0` … `/999`, плюс корень `/` — всего **1001 сообщение**;
* страницы разбиты на 10 слоёв по 100; корень ссылается на весь первый слой, каждая страница —
  на одну страницу следующего слоя, последний слой — ни на что;
* задержка ответа каждой страницы — случайная от 0 до 12 с (в каждом слое одна — ровно 12 с),
  корень отвечает сразу;
* граф зависит только от `student_id` (сумма кодов символов × 37 — зерно генератора).

Самая длинная цепочка — 10 страниц, не больше 10 × 12 = 120 с, отсюда «120 секунд» в задании.
Для `IvanIvanov` самая медленная цепочка занимает ~89 с — ровно столько и идёт обход.
Если запрашивать страницы по очереди, ушло бы больше полутора часов (1000 × ~6 с).

## Проверка

### Тесты

```
./gradlew test
```

Около 20 секунд, сеть не нужна (поднимается встроенный тестовый HTTP-сервер). Проверяется:

* каждое сообщение собрано, каждый URL запрошен ровно один раз — при ромбах, циклах, петлях,
  путях с косой чертой и без;
* порядок: по кодам символов, пустое сообщение первым, одинаковые сообщения не схлопываются;
* 2001 страница по 1 с (корень → 1000 страниц → ещё по одной) обходится за ~2 с, а не за
  2000 с; все запросы выполнялись в виртуальных нитях `spider-…`;
* новый путь запрашивается сразу, а не после медленного соседа (обход не «по уровням»);
* URL с ошибкой попадает в список ошибок, остальное собирается;
* HTTP: разбор JSON (лишние поля, нет `successors`), 404 не повторяется, 5xx повторяется,
  таймаут, нет поля `message`, сервер не запущен;
* обход уменьшенной копии сервера задачи (6 слоёв по 50 страниц, задержки до 0,5 с) по HTTP
  целиком, через `Main`, с записью в файл: результат совпадает с ожидаемым, время — как у самой
  длинной цепочки;
* разбор аргументов командной строки.

### На выданном сервере

Тест `ServerJarTest` сам запускает `Task_J3-server.jar`, обходит его и проверяет, что собраны
ровно пути `/`, `/0` … `/999` (1001 сообщение), без ошибок, отсортированы, и обход занял меньше
130 секунд. Идёт около двух минут, поэтому включается только явно; порт 8080 должен быть
свободен (сервер, запущенный вручную, нужно остановить):

```
./gradlew test -PserverJar=Task_J3-server.jar -PstudentId=IvanIvanov --tests ServerJarTest
```

```
ServerJarTest > crawlsTaskServer() STANDARD_OUT
    student_id=IvanIvanov: сообщений 1001, ошибок 0, 89,3 с, максимум одновременных запросов 100
ServerJarTest > crawlsTaskServer() PASSED
```

### Вручную

1. Запустить сервер со своим `student_id`, затем `java -jar build/libs/J3.jar --out messages.txt`.
2. В итоге должно быть: `обойдено URL — 1001, сообщений — 1001, ошибок — 0`, время — меньше
   120 с, «ждут ответа» в ходе работы — до 100.
3. Число строк в файле — 1001: `wc -l messages.txt` (PowerShell: `(Get-Content messages.txt).Count`).
4. Любое сообщение можно сверить с сервером: `curl http://localhost:8080/425` — его `message`
   есть в файле.

## Файлы

Всё лежит в `src/main/java/org/example`:

| Файл | Что внутри |
|---|---|
| `Main.java` | разбор аргументов, вывод сообщений и хода работы |
| `Spider.java` | «паук»: виртуальная нить на URL, учёт посещённых путей, ожидание конца обхода |
| `PageSource.java` | интерфейс «получить страницу по пути»; в тестах подставляется свой |
| `HttpPageSource.java` | запрос к серверу через `java.net.http.HttpClient`, повторы, разбор JSON |
| `Page.java` | ответ сервера: `message` и `successors` |
| `Log.java` | журнал в stderr: время, имя нити, текст |

Тесты — в `src/test/java/org/example`: `SpiderTest` (без сети), `HttpPageSourceTest`,
`CrawlTest` (обход целиком по HTTP), `ServerJarTest` (выданный сервер), `TestServer` (тестовый
HTTP-сервер).

Зависимость одна — Jackson для разбора JSON; она кладётся внутрь `J3.jar`, так что jar
запускается без дополнительных файлов.

Если путь к домашней папке в Windows содержит кириллицу и тесты не запускаются, см.
[README задачи J1](../J1/README.md#если-путь-к-домашнему-каталогу-содержит-кириллицу).
